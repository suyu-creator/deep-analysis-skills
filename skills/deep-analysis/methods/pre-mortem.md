# Pre-Mortem 轻量自检(闸门 2 收尾用)

> ⚠️ **定位变化**:不再独立闸门。可行性判断并入闸门 2,researcher 调研 + simulator 模拟已覆盖大部分风险,这里只做**7 类死因的快速过一遍**,补充建设性视角看不到的非技术死因(市场不需要 / 时机不对 / 没人用)。

## 核心心理技巧(保留,一行)

用**过去时断言**失败,不用"可能":

> "6 个月后,我们按计划做了,它死得很惨。**为什么死的?**"

"可能失败"让人辩护方案;"已经死了"让人找死因。这是整个方法唯一的价值所在。

## 轻量自检:7 类死因逐类过

对每类问一句"这个死因对本项目成立吗?",挑出成立的 HIGH:

| # | 死因类别 | 自检问句 |
|---|---------|---------|
| 1 | 市场/需求 | 没人想要?需求是假设的没验证?付费意愿是想象的? |
| 2 | 执行/技术 | 比预估难?难点不是我们规划的那个?集成/规模/数据质量咬人? |
| 3 | 人/组织 | 关键人走了?没人真当回事?两个团队都以为对方在做? |
| 4 | 时机/排序 | 依赖没就绪?赶上坏窗口?竞品/监管先动了? |
| 5 | 钱/单位经济 | CAC > LTV?成本模型错了?烧钱跑不到回报? |
| 6 | 采用/习惯改变 | 用户要改习惯不肯改?内部没采用?上手是悬崖? |
| 7 | 外部/监管 | 规则/平台政策/伙伴依赖变了? |

## ⚠️ 每个 HIGH 风险的三件套(缺一不算完成)

对每个挑出的 HIGH 死因,给三样(每样 1 行):

1. **应对方案(必须查 GitHub 实证)** — 用 `search_github` / `read_github_file` 查**同类成熟开源项目怎么解决**(避坑/架构/兜底/反例),把 GitHub 实证并入缓解列;查不到才允许「LLM 推测」。这是"检查到风险时重新查 GitHub 给出完善方案"——不要拿着第一版方案直接下裁决。⚠️ 查询预算与出口见 SKILL.md 闸门 2(L127):≤ min(HIGH 数,12) 次、同类风险合并查询、预算耗尽统一标「未查码=推测」并列为报告局限。
2. **预警信号** — 可观察的先行指标(如"第 2 周激活率 < 20%")。
3. **放弃/转向线** — 预先同意的止损线(如"20 次电话拿 0 个付费 LOI → 转向免费+广告")。

## 建议裁决

- **proceed** / **改(proceed-with-changes)** / **转向(pivot)** / **kill**

⚠️ 裁决 **kill** → 流程终止,主 Agent 写 reflexion 记忆(为什么不该做)。
裁决 **改/转向** → 记录进 phase0 JSON 的 `decisions` 字段。
