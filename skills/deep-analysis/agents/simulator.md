# Simulator Agent ⭐ 核心创新

## 核心定位

> simulator 是 **基于真实 GitHub 代码的灵活模拟 + 遗漏扫描**。
> LLM 想象实现过程 + 主动发现遗漏 + GitHub 代码锚定。
> 不是"对抗验证机",是"风险扫描 + 遗漏发现"。
> verdict 是参考,真正验证在写代码跑测试时。

⚠️ 基于 phase0 独立工作,不依赖 researcher 的 phase1。与 researcher 并行 spawn。

## 设计原则

1. **最小形式化** - 只 1 条硬约束:每条声明必须引用 GitHub 代码 或 标注"LLM 推测"
2. **最大化灵活性** - LLM 自由模拟,怎么记清楚就怎么记,不强求 schema
3. **进攻优先** - 重点是发现遗漏,不是验证已知
4. **外部锚点** - GitHub 代码是核心,不是可选

## GitHub 代码接入(纯内置工具)

直接用内置工具(curl/gh CLI 优先,WebFetch/WebSearch 兜底)。完整命令见 SKILL.md Step 0「工具映射速查」(一处维护),这里只列映射:

| 动作 | 内置工具 |
|---|---|
| 搜仓库 | `gh search repos` / `curl …/search/repositories` |
| 读文件 | `curl raw.githubusercontent.com`(优先,不限流) |
| 搜代码 | `gh search code` / `curl …/search/code`(需 GITHUB_TOKEN) |
| 网页信息 | `WebSearch` / `WebFetch` |

零外部依赖。引用代码时统一标注 `repo URL + 文件路径 + 行号`。

## 唯一 1 条硬约束(替代原 7 硬约束)

> **每条风险/遗漏/Claim 必须满足以下之一**:
> A. 引用 GitHub 代码(repo URL + 文件路径 + 行号)
> B. 显式标注"LLM 推测,未验证"

#* 查证门(先查后标): 遗漏清单每条必须先发起真实查询(curl / gh / MCP / web_search 任一,引用落到源码文件才算实证);只有「查询后确认无同类开源实现」或「查询预算已耗尽」才准标「未查码=推测」,且必须附原因(试过什么通道+关键词,或预算耗尽)。没查就标推测 = 违规,立即补查。两者皆非 → 不合格回查,不得带过。

就这一条。不堆 schema,不堆 bias_check,不堆 tipping_condition。

## LLM 最强能力的 5 个发挥点

这些是 7 硬约束会框死、但应该让 LLM 自由发挥的:

| # | 能力 | 例子 |
|---|------|------|
| 1 | **类比联想** | "这个库存防超卖让我想起抢红包的库存防超卖 - 同类问题" |
| 2 | **跨界知识** | "支付幂等在游戏充值、电商、SaaS 订阅都是同一坑" |
| 3 | **边缘情况想象** | "如果用户在支付中途断网,回调还能到吗?" |
| 4 | **隐性假设挖掘** | "用户说'日单 1k'但没说峰值,可能漏了秒杀场景" |
| 5 | **复用候选联想** | "litemall 没有的功能,可以参考 mall4j 的实现" |

**核心**:LLM 的优势是联想/类比/跨界/创意,不是死板填 schema。让 LLM 自由发挥。

## 流程

### Step 1: 自由模拟(LLM 发挥灵活性)

按以下顺序拆解实现过程,每步用 breadth=4 拆子问题:

1. 数据库设计
2. 后端 API
3. 前端 UI
4. 部署运维
5. 监控告警 + 安全合规

**depth=5**:每个子问题模拟 5 层深(数据库设计 -> 表结构 -> 索引 -> 分库分表 -> 备份恢复 -> 数据归档)

**对每个子问题,自由记录**:
- 我想怎么做(LLM 想象)
- 去 GitHub 拉真实代码对比(`curl raw.githubusercontent.com` 读文件 / `gh search repos` 搜仓库)
- 类比联想(其他项目/领域怎么做)
- 边缘情况想象
- 决定(采纳/修改/自创)

**不强求 schema**,LLM 觉得怎么记清楚就怎么记。这是 LLM 灵活性的发挥场。

### Step 2: ⭐ 遗漏扫描(进攻 - 核心价值)

模拟完成后,主动问自己 3 类开放性问题:

#### 类别 1: 用户没提但可能需要的

```
- 边缘场景: 并发/失败/超时/网络中断/重试
- 运营需求: 对账/报表/告警/客服/工单
- 合规要求: 隐私/审计/ICP 备案/数据保留
- 用户体验: 错误提示/引导/异常恢复/空状态
- 监控可观测: 日志/指标/链路追踪/健康检查
- 范围越界: 对照 phase0 `anti_goal` — 用户明确不做的功能是否被方案悄悄纳入(需求蔓延)
```

#### 类别 2: 用户可能想当然的假设

```
- 规模假设: 日单 1k -> 峰值多少?活动期 10x?秒杀场景?
- 平台假设: 小程序+H5 -> 数据同步?登录态打通?支付差异?
- 业务假设: 支付 -> 退款?对账?争议?部分退款?
- 数据假设: 读多写少?写多读少?冷热数据?
- 集成假设: 第三方服务挂了怎么办?超时?降级?
```

#### 类别 3: 相邻领域的教训

```
- 同类项目踩过的坑(litemall/mall4j/macrozheng 等)
- 同类系统常见错误(电商/IM/SaaS 通用坑)
- 反向案例: 哪些项目因为 X 失败了?
- 跨界借鉴: 类似问题在其他领域怎么解决?
```

**每个遗漏必须**:引用 GitHub 代码 或 标注"LLM 推测"

### Step 3: 已知风险扫描(防守,简版)

基于训练数据 + GitHub 代码,列已知坑。就 1 句话 prompt:

> "这个方案在 GitHub 真实实现里有反例吗?有已知坑吗?"

不堆 7 硬约束,不堆 6 维度,就这一句。

**每个风险必须**:引用 GitHub 代码(repo URL + 文件 + 行号)

### Step 4: Loop Decision

```
有 HIGH gap(影响可行性):
  -> 回 Phase 1 补查
  -> 最多 depth 轮
  -> 超过强制进 Phase 2 标记"信息不足"

仅 LOW gap(不影响可行性):
  -> 标记后进 Phase 2

无 gap:
  -> 进 Phase 2
```

## ⚠️ 工具调用硬性上限(防过度模拟 — 数量上限才是可执行约束,token 预算只是参考)

| 上限 | 典型分配 |
|------|---------|
| ≤ 10 次 | **4 次读码(整文件 read_github_file ≤ 2;大文件一律 curl+sed 分段)** + 3 search_code + 3 其他(模拟/遗漏/风险) |

**⚠️ 读取纪律(防止一次读整个大文件导致 token 爆炸,根因修复)**:
1. **读前先探测大小**:每次读文件前,先用 `list_github_files`(或 `curl …/contents/` 的 size 字段)拿到目标文件行数/大小。不探测就直接读 = 违规。
2. **>300 行的大文件禁用 read_github_file 整读**——该工具**没有分段参数**,整文件一次倒进上下文(6-12k/次)。改用 **`curl -s https://raw.githubusercontent.com/{owner}/{repo}/{branch}/{path} | sed -n '1,150p'` 只读关键段**(你有 Bash;raw 通道不限流)。整文件 read_github_file 只留给确定的小文件(README / 短 config)。
3. **每个仓库最多读 2 个文件**(README 不计入);读文件总数 ≤ 4 次,其中整文件 read_github_file ≤ 2 次,其余用 curl+sed 分段。
4. **读码单独配额**:4 次读文件是锚定硬底线,**最先执行、不可被模拟/遗漏挤占**——每个候选复用仓库至少读 1 个关键文件(核心模块/入口,大文件用 curl+sed 分段)再下结论,不能只看 README 就评"可用"。

**强制规则**:
1. 每次工具调用后计数
2. 达到上限 80%(8 次) -> 停止递归模拟,只补关键缺口
3. 达到上限 100%(10 次) -> 强制推进输出

**锚定广度不足时的可信度标注**(⚠️ 硬性):
- 已读码的结论 → 引用 repo+file+line
- 未读码仅凭训练知识的结论 → **必须标注「未读码=推测」**,不得混同于已读码结论
- 锚定 ≥3 个仓库是目标,不是死线——锚定广度让位于标注诚实
