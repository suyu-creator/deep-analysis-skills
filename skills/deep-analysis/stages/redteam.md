# 阶段: 可行性整合 + 对抗 red-team

Step 3 整合时读本文件前半，Step 3.5 跑对抗时读后半。
⚠️ 强制收尾问题在 SKILL.md 里，别重复问。

## Part A: 可行性整合（Step 3）

researcher + 前模拟产物返回后，主 Agent 直接整合输出：

```
## 可行性整合

### 复用候选 Top 3
| repo | 用途 | 适用性 |

### 遗漏 Top 5（从前模拟）
| 遗漏 | 严重度 | 施工动作 | 来源 |

### 裁决
proceed / 改 / 转向 / kill
理由: <一句话>
```

## Part B: 对抗 red-team（Step 3.5）

用户选「对抗」时执行。扮演 6 个角色攻击方案，**每个角色 3-6 条具体攻击**：

| 角色 | 攻击视角 |
|------|---------|
| 竞争者 | 他们做得更好/更快/更便宜吗？护城河在哪？ |
| 愤怒客户 | 哪里会坏、哪里会卡、哪里让我弃用？ |
| CFO | 成本失控点？该省的没省？投入产出比？ |
| 超负荷工程师 | 哪些功能扛不住峰值/并发/维护？ |
| 监管者 | 合规/隐私/审计红线踩了吗？ |
| 投资人 | 可扩展吗？能撑到规模化的那天吗？ |

每条 🔴/🟨 攻击给解决方案，查 GitHub 找实证（复用优先，硬约束同 researcher）。

### 对抗输出

```markdown
# 对抗 red-team

## 攻击矩阵
| 角色 | 攻击点 | 严重度 | 解决方案 | 来源 |
|------|--------|--------|---------|------|
| 竞争者 | <攻击点> | 🔴 | <解决方案> | repo@file:line / LLM 推测 |
| CFO | <攻击点> | 🟨 | <解决方案> | repo@file:line / LLM 推测 |

## 结论
- <是否调整方案/范围，为什么>
```

对抗结果如有新发现，喂给 Step 4 闭环报告。只处理影响实际交付的攻击点，其余记录即可，不必全修。
