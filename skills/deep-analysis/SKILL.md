# Deep Analysis

单命令走完「需求 → 调研 → 可行性 → 闭环报告」。

## 触发判断

复杂需求才执行，满足任一即复杂：
- 多模块 / 需要架构决策
- 涉及外部集成(支付/登录/第三方 API)
- 需要调研竞品 / 复用候选 / 技术选型
- 存在规模/并发/安全风险
- 用户说"做个 XX 系统/平台"，范围模糊

**简单需求不执行**，直接给 1 句方案。

## 流程总览

```
/deep-analysis <需求>
  ├─ Step 1  需求澄清(1-2 问 → 锁定范围)── 用户确认
  ├─ Step 2  researcher → 前模拟 顺序执行
  │          ┌──────────────┐  ┌──────────────┐
  │          │ researcher   │→ │  前模拟       │
  │          │ GitHub 调研   │  │ 发现未知遗漏   │
  │          │ 产出施工素材   │  │ 遗漏→施工动作  │
  │          └──────────────┘  └──────────────┘
  ├─ Step 3  可行性整合(复用候选 + 遗漏清单)── 收尾必问: 方向 OK? 要不要跑对抗?
  ├─ Step 3.5 对抗 red-team(用户选「跑」才执行)
  └─ Step 4  三阶段: 草案→用户确认→后模拟→用户确认→写 CLOSURE.md
        ⤴ 任意时刻冒出新需求 → 暂停，按硬规则 4 处理
```

**双模拟分工**：
- **前模拟（Step 2）**：发现你不知道自己不知道的事 → 遗漏清单
- **后模拟（闭环自检，Step 4）**：验证计划覆盖了所有已知需求 → 覆盖表 + 依赖检查 + 来源诚实

## Step 1: 需求澄清

问 1-2 个关键问题（平台？规模？已有代码还是全新？），锁定范围后用户确认。

输出 `phase0`：
```json
{
  "requirement": "<需求原文>",
  "platform": "<平台>",
  "scale": "<规模>",
  "existing_code": "<greenfield / 已有项目路径>",
  "anti_goal": "<明确不做哪些>"
}
```

## Step 2: 调研 + 前模拟（顺序执行）

基于 phase0，主 Agent 顺序执行两个阶段（不 spawn 子代理，产物留在对话内传递）：

- **researcher** — Read `stages/researcher.md`，GitHub 调研同类项目，产出施工素材（复用候选 + 施工信息）
- **前模拟** — Read `stages/simulator.md`，基于 phase0 + researcher 产物，模拟实现过程扫遗漏，每项遗漏配施工动作

顺序执行 → 前模拟拿到 researcher 的复用候选再模拟，零重复搜索、信息充分。

## Step 3: 可行性整合

researcher + 前模拟产物返回后，主 Agent 直接整合输出：

```
## 可行性整合

### 复用候选 Top 3
| repo | 用途 | 适用性 |

### 遗漏 Top 5（从前模拟）
| 遗漏 | 严重度 | 施工动作 | 来源 |

### 裁决
proceed / 改 / 转向 / kill
理由: <一句话>
```

⚠️ **Step 3 强制收尾问题（必须问，答完才进 Step 4）**——方向确认 + 对抗决策一次问完：

> **"方向对吗？可行性 OK 吗？要不要跑对抗 red-team？（跑 / 跳过）"**

即使用户回答「直接下一步」/「确认」，**也必须追问对抗决策**（跑 / 跳过），得到明确回答后才进 Step 4。不问对抗就出闭环报告 = 违规。

### Step 3.5: 对抗 red-team（在写闭环报告之前执行）

用户选「对抗」时执行。扮演 6 个角色攻击方案：竞争者 / 愤怒客户 / CFO / 超负荷工程师 / 监管者 / 投资人。每个角色 3-6 条具体攻击。每条 🔴/🟨 攻击给解决方案，查 GitHub 找实证。对抗结果如有新发现，喂给 Step 4 闭环报告。

⚠️ **Step 3.5 强制收尾（必须问，答完才进 Step 4）**——汇报对抗结果后必须问：

> **"对抗结果 OK 吗？要调整方案/范围吗？确认后我写闭环报告。"**

未得到用户明确确认就写闭环报告 = 违规。

用户选「跳过」→ 直接进 Step 4。

## Step 4: 输出闭环报告

⚠️ **前置硬约束：必须在 Step 3 完成对抗决策询问（跑/跳过）、且 Step 3.5 对抗结果获用户确认之后才开始 Step 4**。未确认就开始 = 违规。

### 流程（三阶段，顺序执行）

```
Step 4a: 先发草案给用户确认
  → 输出骨架 + 复用施工单 + 路线图 + 自研施工单（对话中展示，不写文件）
  → 问用户: "方案 OK 吗？确认后我跑后模拟验证。"

Step 4b: 用户确认后，跑后模拟（闭环自检）
  → 模拟执行计划，走不通就修，修完再走
  → 输出走查结果 + 修复记录 + 需用户决策项

Step 4c: 后模拟通过后，写 CLOSURE.md 落盘
  → 完整闭环报告 = 草案 + 后模拟结果
```

### Step 4a: 草案模板（对话展示，不写文件）

```markdown
# 闭环报告（草案）: <项目名>

## 1. 项目骨架
- 目录结构（精确到文件）
- 技术栈 + 版本号
- 初始化命令（复制粘贴就跑）

## 2. 复用施工单
| 模块 | 来源(repo@file) | 复用方式 | 需改动 | 理由 |
|------|-----------------|---------|--------|------|
| <模块A> | repoX@src/auth/login.ts | 直接复制 | 去掉 OAuth，只留邮箱 | 需求只需邮箱登录 |

## 3. 实施路线图
### Phase 1: <名称>（依赖: 无）
- [ ] 步骤 1 — 做什么、参考什么
- [ ] 步骤 2
- 验证: <怎么算做完>

## 4. 自研施工单
| 模块 | 为什么没得复用 | 实现思路 | 参考 |
|------|--------------|---------|------|
```

⚠️ **Step 4a 强制收尾**——必须问用户确认：

> **"方案 OK 吗？确认后我跑后模拟验证。"**

### Step 4b: 后模拟（闭环自检）

> **后模拟 = 模拟执行这个计划，走一遍看能不能通。不通就修，修完再走，直到通为止。核心目标是验证整个流程可执行，不是逐项打勾。**

#### 走查时参考以下材料（非强制，辅助发现漏洞）

| 参考材料 | 来源 | 怎么用 |
|---------|------|--------|
| 前模拟遗漏清单 | Step 2 | 每项遗漏在路线图里被覆盖了吗？没覆盖的补上 |
| 可行性裁决 | Step 3 | proceed 的前提条件满足了吗？改/转向的调整落实了吗？ |
| 对抗结果 | Step 3.5（如有） | 只处理影响实际交付的攻击点，其余记录即可，不必全修 |
| 复用候选 | Step 2 researcher | 计划里引用的复用来源，实际能拿到吗？ |
| phase0 anti_goal | Step 1 | 方案有没有悄悄纳入明确不做的功能？ |

#### 走查方式
挑 1-2 个核心用户场景，按路线图 Phase 顺序逐步走查。每一步：
1. 这一步需要的输入（数据/模块/配置）在前面的步骤里产出了吗？
2. 参考上表扫一眼，有致命漏洞吗？

#### 走不通时的处理

| 情况 | 判断标准 | 处理方式 |
|------|---------|---------|
| 简单 | 缺配置、漏步骤、少依赖声明 | **LLM 直接补**，记录修复 |
| 中等 | 需要找方案但方向明确（如"缺一个限流中间件"） | **拉 researcher 流程**，搜 GitHub 找现成方案，补上后继续走 |
| 复杂 | 动架构、动范围、多模块冲突、推翻前一步决策 | **停下来问用户**，说明断点和选项 |

#### 输出

```markdown
### 场景走查: <场景名>
| 步骤 | Phase | 能通？ | 问题 | 处理 |
|------|-------|--------|------|------|
| 用户注册 | Phase 1 | ✅ | — | — |
| 下单支付 | Phase 2 | ❌ | 支付回调没处理 | 中等 → 搜 repoX@src/payment/webhook.ts，补进 Phase 2 |

### 修复记录
| # | 原问题 | 修复 | 来源 |
|---|--------|------|------|
| 1 | 支付回调缺失 | 复用 repoX webhook 模块 | repoX@src/payment/webhook.ts |

### 需用户决策
- <断点描述> — 选项 A / 选项 B
```

#### 退出条件
- 核心场景全部走通，或
- 剩余问题全是「需用户决策」级别
- 达到任一条件 → 进入 Step 4c

### Step 4c: 写文件

后模拟通过后，将完整闭环报告（草案 + 后模拟结果）写入 `CLOSURE.md`。

每个模块必须标 **复用 / 改造 / 自研**，复用/改造必须标注来源 repo + 文件路径。

## 硬规则

1. **复杂需求才触发** — 简单需求直接忽略
2. **复用优先** — 先搜 GitHub，有现成直接引用，不从零想方案
3. **每条声明标注来源** — GitHub 代码(repo@文件:行号) 或 「LLM 推测」
4. **需求变更即停** — 任意时刻冒出新需求（流程中/闭环报告后）：暂停 → 记录 → 评估影响 → 回退对应 Step（动范围→Step1、动方案→Step2、仅追加→闭环报告需求池）→ 用户确认后继续。绝不默默按旧需求做到底
