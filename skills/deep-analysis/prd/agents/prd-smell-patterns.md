# Requirements Smell Patterns

Canonical list of anti-patterns in requirements. Used by the PRD reviewer
and its sub-agents when evaluating FR and AC quality.

## Linguistic Smells

Source: Femmer et al., TU Munich, 2017 — adapted for PRD review.

- **Vague verb**: "handle", "manage", "process", "support", "deal with" — require a concrete verb (display, send, reject, store, calculate)
- **Loophole**: "if possible", "as appropriate", "when feasible", "as needed", "where applicable" — gives dev permission to skip
- **Ambiguous pronoun**: "it", "they", "this" without clear antecedent in same sentence
- **Passive voice hiding actor**: "is validated", "is shown" — WHO does it? The system, the API, the user?
- **Open-ended list**: "etc.", "and so on", "such as" used as substitute for a complete list
- **Superlative/comparative**: "fastest", "better", "optimal" — unmeasurable without baseline
- **Incomplete conditional**: "if X then Y" without specifying what happens when X is false
- **Subjective language**: "user-friendly", "intuitive", "clean", "simple", "seamless" — not testable
- **Temporal comparison**: "today the code does X", "currently", "legacy", "old implementation", "supersedes", "existing code", "key differences from current behavior", "this replaces the old" — the PRD describes WHAT TO BUILD, not what exists or what changed. If old artifacts need cleanup, that's a separate chore ticket, not PRD content.
- **Implementation delegation**: "via someFunction()", "using utilityName", "formatted by formatTime", "whatever X returns", "as returned by" — delegates the requirement to current code instead of defining expected behavior. Replace with the observable output (format, thresholds, concrete examples). This includes feature-layer utility function names (`getAvatarColor`, `formatPhone`, `parseAmount`) — any function defined in `src/features/*/utils/`, `src/utils/`, or shared utility modules that is not a public DS component prop or documented Web/Browser API. Describe the behavior observably and let the Component Mapping or implementation tickets resolve the utility.
- **Under-specified render**: a display requirement that names a format but not its determinant — "locale-aware date" without a timezone, "formatted amount" without currency/minor-unit handling, "the list of X" without an ordering rule. The text reads as decided, so it draws no clarifying question, but two implementations will show different things to the customer. Require the determinant, not a longer format name.

## Behavioral/Technical Separation Smells

Source: PRD behavioral/technical separation rules — see `~/.claude/skills/deep-analysis/prd/rules/behavioral-separation.md`.

These smells detect technical implementation details that have leaked into the behavioral layer (FRs, ACs, Edge Cases, Key Entities). The behavioral layer should be verifiable by a QA engineer without reading source code. Technical details belong in the Technical Contract, referenced via `[V#]` vocabulary markers.

- **API field leak**: Raw API field names in behavioral requirements — `order_id`, `shipping_method_code`, `deleted_at`, `avatar_url`, `currency_code`. Replace with semantic concept names: "order identifier", "shipping method label", "soft-delete marker". Each semantic name maps to exactly one API field, defined in the per-endpoint vocabulary table.
- **Enum leak**: API enum values listed in FRs/ACs — `cancelled`, `cancelling`, `returnRequestedByCustomer`, `"EXPRESS SHIPPING"`, `"onHold"`, `"gift-card"`. Replace with semantic group names: "cancelled status", "on-hold stage". The full enum-to-label mapping belongs in the Technical Contract.
- **Wire-detail leak (paths, status codes, headers)**: Endpoint paths or URL templates, raw HTTP status codes, and header names in behavioral requirements — `/order/<id>`, `POST /v1/passcode/verify`, `HTTP 201`, `429`, `Retry-After`. These all fail the **rename test** — renumbering a status code or renaming a path changes nothing the user observes. Replace with semantic destinations and outcomes: "the order details page", "when the backend confirms the passcode", "when the backend rejects the passcode as incorrect", "when the backend rate-limits further attempts". Paths map in Route Mapping; status codes and headers map in Error Classification / per-endpoint Error Handling. In `slim` mode this pattern also covers transport taxonomy in analytics properties — an `error_status_code`-style property, status-number encoding rules ("`0` for transport failure"), or wire-level failure classes (`transport`, `http_error`, `parse_error`) referenced from an FR/AC; failure classes are named by what they mean to support (`unreachable`, `rejected`, `unusable_response`, `incomplete_record`) and the wire-to-class mapping is dev-owned (see the Forbidden list in `~/.claude/skills/deep-analysis/prd/rules/behavioral-separation.md`). Slim mode also bars code wiring referenced from an FR/AC — a route path constant (`paths.inviteFriends`), a repo file path (`src/…`, `packages/…`, `.ts`/`.tsx`), a component class name where an SR alias exists; name the concept and leave the wiring to the implementation ticket (`ds-gap`/`api-canonical-gap` issue references, Dependencies rows for a product-level blocker that is itself code, and commit-pinned evidence permalinks are the allowed homes).
- **User-facing text in requirement**: Any literal user-facing string in FRs/ACs — headings, body text, button labels, toasts, error/empty-state text — and any localization-key path (`orders.list.title`, `checkout.empty.body`). Copy, localization keys, and translations are **design-owned deliverables, not PRD content** (see `~/.claude/skills/deep-analysis/prd/rules/behavioral-separation.md`). Flag every literal string and every key. Replace with copy *intent by semantic role*: "render an empty state explaining no results were found", "display an error telling the user the codes did not match and to retry". Do NOT reference a Localization Keys table — the PRD no longer contains one. **Exception:** wording mandated by law/compliance/contract stays as a quoted constraint with its source cited.
- **Analytics event name inline**: Event names or payload schemas in FRs/ACs — `checkout_page_viewed`, `checkout_step_failed`, `order_id: string`. Replace with semantic trigger names: "the page-viewed analytics event", "the step-failed analytics event (see Analytics Events table)". The Analytics Events table is the source of truth for event names and properties.
- **Framework terminology**: Library-specific or framework-specific concepts in behavioral requirements — e.g. "staleTime", "React Router state". Replace with observable behavior: "data refreshes after successful mutations", "data refreshes when the user navigates away and back". Framework details belong in the Technical Contract. This pattern splits into three tiers with three different remedies — library/framework terms **relocate** to the Technical Contract; CS jargon describing testable behavior is flagged for **rephrasing in place** and stays as an FR; product decisions and platform concepts that sound technical are **not this pattern — do NOT flag them**. The **implementation-mechanism sub-category** (apply the QA-observability test) — *where or how* a value is stored or transported — cannot be observed by using the app, so it relocates to the Technical Contract; do not reword it into an FR/AC. Read "Quick Reference: Forbidden in the Behavioral Layer" and "Quick Reference: Allowed in the Behavioral Layer" in `~/.claude/skills/deep-analysis/prd/rules/behavioral-separation.md` for the canonical per-tier item lists before judging this pattern.
- **Design decision in requirement**: Any language that chooses *how* the UI renders something rather than *what* the user sees or does. Apply the **designer-choice test**: could a designer reasonably present the same behavior with a different component, layout, emphasis, or visual treatment? If yes, the PRD must not prescribe it. This covers emphasis/variant qualifiers ("primary, filled button", "outlined"), layout arrangements that prescribe CSS structure, visual treatments (pixel values, color variants, spacing tokens), and breakpoints — on any platform. Replace with behavioral intent. **Over-specification (altitude):** an AC that enumerates several visual elements or reads as a screen layout ("heading X, a 6-dot indicator, and a numeric keypad with delete") is a design spec, not a behavioral criterion — flag it; that furniture belongs to the design source (the Visual References section in `full` mode; the design itself in `slim` mode) and the Screen Flow section, and the AC should assert one observable outcome. **Design-mechanism prescriptions (`slim` mode — same violation class as wire leaks):** content ordering/stacking ("single column", "stacked in that order"), skeleton/placeholder composition ("shaped like …"), live-region politeness levels ("announce politely/assertively"), and focus targets or choreography ("focus stays on the retry affordance") — the PRD may state perceivable outcomes and their priority, never the treatment; a focus rule passes only as an outcome ("an ignored repeat activation must not trap or move focus"). **Do NOT flag (product, not design)**: the product-requirement carve-out is enumerated in "Quick Reference: Allowed in the Behavioral Layer" in `~/.claude/skills/deep-analysis/prd/rules/behavioral-separation.md` — read it before flagging this pattern.

**Vocabulary-aware checking**: When semantic vocabulary files exist for the initiative's endpoints (`semantic-vocabulary/`), cross-reference them. If a vocabulary file maps `shipping_method_code` to "shipping method label" and the FR uses "shipping method" or `shipping_method_code`, both are FAIL — the vocabulary file's semantic name is the only acceptable term in the behavioral layer.
